Git worktree로 작업 공간 나누기

브랜치와 작업 폴더의 차이를 이해하고, 여러 에이전트가 수정할 공간을 나눕니다.

Git worktree는 한 저장소에 작업 폴더를 추가하는 기능입니다. 각 폴더에서 서로 다른 브랜치를 열어 두면, 진행 중인 작업을 그대로 둔 채 다른 작업을 시작할 수 있습니다. 여러 에이전트에게 파일 수정을 맡길 때도 각자의 작업 공간을 정하는 데 도움이 됩니다.

브랜치와 작업 폴더를 구분하기

브랜치를 만드는 일과 작업할 폴더를 만드는 일은 다릅니다. 브랜치를 여러 개 만들어도 현재 폴더에서 보이는 파일은 현재 checkout한 상태입니다. 이 구분을 먼저 이해하면 worktree가 필요한 이유도 명확해집니다.

Branch, worktree, clone의 역할
개념뜻무엇을 늘리는가
Branch커밋을 가리키며 이동하는 참조변경 이력의 갈래
Worktree같은 저장소에 연결된 작업 폴더와 상태동시에 열어 둘 작업 공간
Clone새 디렉터리에 복제한 저장소브랜치 참조 등을 별도로 관리하는 저장소

브랜치의 정의는 Git 공식 책, 저장소 복제 동작은 git-clone 문서에서 확인할 수 있습니다. 로컬 clone에는 저장 공간을 절약하는 방식도 있으므로, clone을 항상 모든 데이터를 중복 저장하는 방법으로 설명하면 부정확합니다.

이력은 공유하고 작업 공간은 나누기

아래 그림에서 세 폴더는 같은 저장소에 연결되어 있습니다. task-a의 파일을 고쳐도 task-b 폴더의 파일이 실시간으로 바뀌지는 않습니다. 커밋과 브랜치 참조를 함께 사용하는 것과, 작업 파일을 함께 수정하는 것은 구분해야 합니다.

여러 worktree 사이에서 공유하거나 따로 유지하는 상태
공유폴더별로 분리
커밋 객체와 이력checkout한 작업 파일과 미커밋 변경
브랜치·태그 참조현재 위치를 나타내는 HEAD
기본 저장소 설정커밋할 내용을 준비하는 index

공유 데이터와 개별 상태의 경계는 Git 저장소 구조 문서에 설명되어 있습니다. 같은 저장소 안에서 이력을 참조할 수 있어도 다른 브랜치의 변경을 내 작업에 반영하는 과정은 별도로 필요합니다.

같은 브랜치에 worktree를 여러 개 둘 수 있나요?

일반적인 수정·커밋 작업에서는 worktree마다 서로 다른 로컬 브랜치를 사용하는 방식을 권장합니다. Git은 같은 저장소의 다른 worktree에서 이미 체크아웃한 브랜치를 새 worktree에 다시 체크아웃하는 것을 기본적으로 거절합니다. git worktree add의 --force로 예외를 허용할 수는 있지만, 이 보호장치를 우회하는 방식은 병렬 개발의 기본 운영 방식으로 권장하지 않습니다. Git 공식 문서: 기본 제한과 force 옵션

이는 예외 없는 1:1 규칙이 아니라 Git의 기본 보호 정책에 맞춘 운영 권장입니다. Orca의 공식 작업 모델도 각 worktree에 자체 브랜치와 작업 파일을 두는 방식으로 설명합니다. Orca의 worktree 모델

같은 브랜치를 강제로 공유하면 왜 위험할까요?

예를 들어 두 worktree가 같은 feature/login 브랜치를 체크아웃했다고 가정해 보겠습니다. A에서 커밋하면 공유하는 브랜치가 새 커밋으로 이동합니다. 하지만 B의 파일과 index는 이전 상태로 남습니다. B에서 이를 확인하지 않고 커밋하면 A가 반영한 변경을 의도치 않게 되돌리는 내용까지 포함할 수 있습니다.

이 위험은 브랜치 참조를 공유하면서 작업 파일과 index는 따로 유지하는 구조에서 나옵니다. 위 예시는 그 구조와 커밋 동작을 조합해 설명한 것입니다. Git 저장소 구조, index로 커밋을 만들고 브랜치를 갱신하는 동작

같은 출발점과 같은 브랜치는 다릅니다

같은 저장소에서 여러 worktree를 사용할 때
구성사용 기준
A는 feature/login, B는 feature/search일반적인 병렬 개발에 권장합니다. 둘 다 같은 main 커밋에서 출발해도 됩니다.
A와 B가 모두 feature/login기본적으로 거절됩니다. 강제로 중복 체크아웃해 병렬 수정하는 방식은 피합니다.
같은 커밋을 detached HEAD로 열기가능합니다. 브랜치를 체크아웃하지 않고 특정 커밋을 살펴보는 방식입니다.
보충 · 브랜치 없이 열기와 같은 폴더에서 협업하기

빌드나 검토를 위해 특정 커밋을 따로 열 때는 --detach를 사용할 수 있습니다. 계속 개발하고 변경을 보존하려면 별도 브랜치를 만들어 관리하는 편이 명확합니다. Git의 detach 옵션

여러 에이전트가 하나의 worktree 폴더를 사용하는 것은 같은 브랜치를 여러 worktree에 중복 체크아웃하는 것과 다릅니다. 이 경우 파일과 index도 함께 사용하므로 수정할 파일과 Git 작업의 담당자를 정해야 합니다.

세 줄로 작업 공간 만들기

다음은 개념을 확인하는 교육용 명령입니다. 현재 위치는 기존 저장소 안이며, 로컬 main 브랜치가 존재한다고 가정합니다. 새 브랜치명과 목적지 경로는 아직 사용하지 않아야 합니다. 출발점은 원격의 최신 상태가 아니라 명령을 실행할 때 로컬 main이 가리키는 커밋입니다.

git worktree add -b meetup/task-a ../repo-task-a main
git worktree add -b meetup/task-b ../repo-task-b main
git worktree list

첫 두 줄은 새 브랜치와 작업 폴더를 만듭니다. 끝의 main은 출발점이며, 실제로 체크아웃하는 브랜치는 각각 meetup/task-a와 meetup/task-b입니다. 마지막 줄은 연결된 worktree를 보여 줍니다. 기존 폴더의 미커밋 변경과 untracked 파일은 자동 복사되지 않습니다. 자세한 동작은 git-worktree 문서를 참고하세요.

분리한 뒤에도 필요한 일

Worktree를 쓰면 수정 공간을 구분하기 쉬워집니다. 그러나 작업을 잘게 나누고, 결과가 서로 맞는지 확인하고, 통합 여부를 판단하는 일은 남습니다. 팀에서는 다음 세 가지를 함께 정하는 것이 좋습니다.

  • 통합 책임: 두 브랜치가 같은 영역을 다르게 수정하면 merge 충돌이 생길 수 있습니다. 충돌 없이 합쳐져도 기능이 함께 동작하는지는 테스트와 리뷰로 확인합니다. 충돌 처리 자체는 git-merge 문서의 범위입니다.
  • 실행 환경: 개발 서버 포트, 외부 데이터베이스, 공유 캐시는 프로젝트 방식에 맞춰 구분합니다. 폴더가 따로 있어도 같은 자원에 접근할 수 있습니다. 의존성과 환경 파일의 준비 방법도 정해 두면 좋습니다.
  • 접근 권한: Worktree 자체는 에이전트의 파일 접근 권한을 제한하지 않습니다. 같은 사용자 권한으로 실행된다면 다른 폴더에 접근할 수 있습니다. 접근 제한이 필요하면 실행 도구의 sandbox나 운영체제 권한 등 별도의 장치를 사용합니다.

이렇게 작업 공간을 마련했다면, 다음 단계는 담당자와 의존 관계를 정하는 것입니다. 누가 무엇을 맡고, 어떤 결과를 기다리며, 완료를 어떻게 확인할지 연결하는 절차가 오케스트레이션입니다.
